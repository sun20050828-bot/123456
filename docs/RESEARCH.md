# 研究生课程设计：如何做成一项可信的系统研究

## 已完成的可检查成果

- 从状态机推导的数据模型、事务边界和租约所有权检查。
- 独立进程竞争测试与真实进程故障注入，包含副作用 / ack 的崩溃窗口。
- 正确模型和错误模型的有限状态枚举对照。
- 带原始数据和环境元数据的重复性能实验。
- 可读的保证边界与失败条件，不使用 exactly-once 营销措辞。

这满足研究生系统课程项目的基本深度，但论文级结论还需要更大规模实验、相关工作综述、
明确的新机制及更多运行环境。当前结果是课程研究原型，不是已发表论文。

## 可扩展成课题的方向

| 方向 | 机制变化 | 验证 / 对照 |
|---|---|---|
| 锁粒度与批量调度 | 批量 claim、ack 聚合 | 1/8/32 batch；吞吐、P99、崩溃重复放大 |
| 过期回收公平性 | 分批 recover、priority aging | 大量过期任务 + 新任务混合；低优先级等待 |
| 自适应租约 | 历史处理时间分位数估计租约 | 重尾 handler；错误回收率、恢复时间、renew 写入成本 |
| 重试风暴 | full jitter / decorrelated jitter | 同时故障 1000 任务；重试峰值、完成延迟 |
| 外部一致性 | transactional outbox + inbox 去重 | 多数据库提交窗口、handler 重入与幂等契约 |
| 存储后端比较 | SQLite / PostgreSQL SKIP LOCKED | 同等 durability、相同 workload、相同计时边界 |
| 模型与实现一致性 | 状态机测试器生成 API 轨迹 | 独立参考模型、历史回放、线性化点检查 |

尚未实现的扩展不会列为现有功能。

## 答辩时应能回答

1. 为什么 claim 使用 BEGIN IMMEDIATE，而不是先 SELECT 再无条件 UPDATE？
2. 获得锁后采样时间解决了什么问题？commit 期间越过 deadline 如何定义语义？
3. 随机 token 与单调 generation 的职责分别是什么？只检查 state 有何反例？
4. 为何老 worker 可以继续执行 handler，却不能 ack？外部系统如何处理它？
5. key 相同 payload 不同是返回原任务还是拒绝？done 之后再次提交如何处理？
6. 达到 max_attempts 后还能宣称至少一次吗？活性依赖哪些假设？
7. 为什么多 worker 可能更慢？如何把 handler 时间和存储瓶颈区分开？
8. 三次重复能说明什么，不能说明什么？为何保存 worker_counts 与原始 trial？
9. SQLite FULL 和 NORMAL 在 DELETE/WAL 下耐久性区别如何验证？
10. 本模型检查了设计还是实现？怎样扩展到多任务和实现历史验证？

## 建议后续实验

每组十次以上重复；worker=1/2/4/8；任务数至少 10000；handler=0/2/20ms；
queue 深度、payload 大小、数据库膨胀、故障比例分别控制。
测量锁等待、吞吐、P99、Jain 公平指数、重复执行次数及 dead 比例。
先写出假设，再运行实验；保留不符合预期的结果。
